Futex

futex = Fast Userspace muTexes（快速用户空间互斥体），2002 年由 IBM 的 Hubertus Franke 等人在 Linux 上提出，2.5.7 起进入内核。它不是一把锁，而是一份用户态与内核态的合作契约：

[!tip] 一句话本质 无竞争时在用户态用一条原子指令完成加解锁；仅当真的发生竞争时，才通过 futex(2) 系统调用陷入内核，把线程挂到内核按地址索引的等待队列上休眠。

相关笔记：[[多线程]]、[[内核中的同步]]、[[进程：调度]]、[[内存模型]]、[[协程]]

1 第一性原理：为什么需要 futex

从成本模型出发，只有两个事实：

  1. 锁在绝大多数时刻是无竞争的。一个线程拿到锁、出临界区的窗口内，往往根本没别人来抢。
  2. 系统调用比原子指令贵几个数量级。系统调用要陷入内核、上下文切换；原子指令（x86 的 cmpxchg/lock 前缀）虽比普通指令贵，但仍在用户态完成。

而 futex 之前的同步原语（System V 信号量 semop、文件锁 flock）把两件事都做错了：每次加锁/解锁都无条件陷入内核去操作内核对象——哪怕根本没人竞争。

因此 futex 的设计必然是两层的：

层 形态 职责
用户态 一个 32 位原子变量（位于共享内存） 快速路径：CAS 判定无竞争，直接完成
内核态 futex(2) 系统调用 慢速路径：休眠等待 / 唤醒等待者

[!warning] futex 机制 ≠ futex 系统调用 直接拿 futex(2) 写应用代码是错的。futex 机制的性能来自用户态那一半（glibc 已替你写好），系统调用只是慢速路径。应用层永远用 std::mutex / pthread_mutex。

2 全景时序

以两线程竞争 pthread_mutex 为例（state：0 无主 / 1 有主无等待 / 2 有主有等待）：

sequenceDiagram
    participant T1 as 线程 T1
    participant U as 用户态锁变量 state
    participant K as 内核 futex
    participant T2 as 线程 T2

    T1->>U: CAS(0 → 1) 成功
    Note over T1,U: 无竞争，纯用户态，零系统调用
    T2->>U: CAS(0 → 1) 失败（state==1）
    T2->>U: 置 state = 2（标记有等待者）
    T2->>K: futex(&state, FUTEX_WAIT, 2)
    K->>K: 校验 *uaddr==2 → 挂入哈希桶等待队列，休眠
    T1->>U: 临界区执行完毕，unlock
    T1->>U: xchg(state → 0)，发现旧值==2
    Note over T1: 旧值>1 说明有人在睡，必须叫醒
    T1->>K: futex(&state, FUTEX_WAKE, 1)
    K->>T2: 移出队列，置 TASK_RUNNING，重新调度
    T2->>U: 返回用户态重抢：CAS(0 → 2)，成功

关键在 unlock 一侧：只有发现旧值是 2（曾有等待者）才进内核唤醒——这就是「无竞争不系统调用」在释放路径上的体现。

3 futex 系统调用

参数 含义
uaddr 用户态共享内存中 futex 变量的地址（内核只存地址，不给它赋予任何语义）
futex_op = FUTEX_WAIT 若 *uaddr == val 则休眠，挂到 uaddr 对应的等待队列；否则立即返回 EAGAIN
futex_op = FUTEX_WAKE 最多唤醒 val 个等待在 uaddr 上的任务，返回实际唤醒数
FUTEX_PRIVATE_FLAG op 的低位标志：声明 futex 仅用于进程内线程同步，内核可走更快的 key 计算路径
其他 op FUTEX_REQUEUE、FUTEX_WAKE_OP、FUTEX_LOCK_PI（优先级继承）等进阶操作

[!note] EAGAIN 防「丢失唤醒」 FUTEX_WAIT 要求调用者先读 *uaddr 再传入。若在「读之后、入睡之前」值被人改了，说明该事件已在半路发生——内核拒绝入睡并返回 EAGAIN，让调用者回到用户态重新检查条件。没有这个约定，唤醒方在检查之后、入睡之前的缝隙里发出的 FUTEX_WAKE 就会永远丢失。

两个必须写进肌肉记忆的语义：

  1. 虚假唤醒（spurious wakeup）：FUTEX_WAIT 可能无缘无故返回（信号、races），所以等待逻辑必须放在循环里重新验证条件。
  2. 返回值语义：WAIT 成功返回 0；WAKE 返回唤醒的任务数（可能为 0——没人可叫不算错误）。

4 用户态视角：mutex 的三态状态机

Ulrich Drepper《Futexes Are Tricky》中的经典实现（glibc 低层锁 lll 与 Go runtime 同款思路），用一个 std::atomic<int> 承载三个状态：

stateDiagram-v2
    [*] --> s0: 初始
    s0: 0 = 无锁
    s1: 1 = 有锁，无等待者
    s2: 2 = 有锁，有等待者
    s0 --> s1: lock: CAS(0→1) 成功（快速路径）
    s1 --> s2: 新的 lock 失败者 CAS(1→2)，随后 FUTEX_WAIT
    s2 --> s2: FUTEX_WAIT 中休眠
    s1 --> s0: unlock: fetch_sub 后旧值==1（快速路径，无需唤醒）
    s2 --> s0: unlock: 旧值==2 → 置 0 并 FUTEX_WAKE
    s2 --> s1: 被唤醒者重抢成功

[!note] 为什么需要状态 2？ 它是唤醒方视角的“可能有睡着的等待者”标记。没有它，unlock 无法区分「没人等，直接返回」和「有人在内核里睡，必须叫醒」，要么每次 unlock 都白进一次内核，要么丢失唤醒。glibc lowlevellock.h 的注释把三态写作 0 / 1 / >1，同一个意思。

5 内核视角：按地址索引的哈希等待队列

内核里 futex 的本体是一张全局哈希表，把「用户态某地址上睡着的任务」组织起来。Eli 的转述：futex 是内核替用户空间维护的队列。

flowchart LR
    subgraph 用户态传入
        UA[uaddr + flags]
    end
    UA -->|get_futex_key| KEY[futex_key]
    KEY -->|jhash| HB["全局哈希表 __futex_data<br/>256 × num_possible_cpus 个桶"]
    HB --> B0["futex_hash_bucket<br/>spinlock_t lock<br/>plist_head chain（优先级链）"]
    B0 --> Q1[futex_q: task_struct + key + plist 节点]
    B0 --> Q2[futex_q ...]

5.1 关键数据结构

key 的推导是「private/shared 之分」的根源：

场景 虚拟地址唯一吗 key 构成 成本
线程间（private） 是——同进程线程共享地址空间 (mm_struct 地址, 虚拟地址) 一次比较，极快
进程间（shared） 否——各进程映射地址不同 (inode->i_seq, page->index, 页内偏移)，即物理页定位 需查页表取物理页，慢得多

默认走 private 快路径；FUTEX_PRIVATE_FLAG 缺失时才按 shared 处理。把这个区分暴露给用户态，本身就是一项性能优化——绝大多数锁是线程锁。哈希表在 futex_init（core_initcall）时按 256 × CPU 数 建桶，配合桶级自旋锁把争抢分散。

6 从 std::mutex 到 futex：完整调用链

std::mutex → glibc-nptl → futex(2)

flowchart TD
    A["C++ std::mutex::lock()"] -->|__gthread_mutex_lock| B["glibc pthread_mutex_lock<br/>（nptl/pthread_mutex_lock.c）"]
    B -->|类型==TIMED_NP 默认锁| C["LLL_MUTEX_LOCK 宏"]
    C --> D["__lll_lock 宏：<br/>CAS(lock, 1, 0) 成功 → 完成（纯用户态）"]
    D -->|失败| E["__lll_lock_wait_private（汇编）<br/>lock 置 2 → syscall SYS_futex"]
    E --> F["内核 do_futex → futex_wait"]

glibc 侧 pthread_mutex_t 的状态字段与分发逻辑：

__kind 的第 8 位 PTHREAD_MUTEX_PSHARED 正对应 FUTEX_PRIVATE_FLAG——用户态声明与内核 key 快慢路径一一衔接。

Android bionic 的 pthread_mutex是同一思想的精简版：atomic_exchange(state, locked_contended) != unlocked 则 __futex_wait_ex；unlock 时 exchange(state, unlocked) == locked_contended 则 __futex_wake_ex。pthread_cond（wait/signal）、pthread_rwlock 也都落在 futex_wait/futex_wake 上。Java 侧：synchronized 由 ART 虚拟机实现，monitor 锁先 CAS 自旋，迟迟拿不到则膨胀为重量级锁，最终 futex(FUTEX_WAIT_PRIVATE) 休眠；JUC 的锁体系底层同样收敛到 futex。

Go runtime 不依赖 libc，自建锁：sync.Mutex 快速路径原子交换，慢速路径 runtime.lock（lock_futex.go，常量 mutex_unlocked/locked/sleeping = 0/1/2）→ futexsleep → FUTEX_WAIT_PRIVATE。

7 内核优化前沿

针对「同步 IPC 场景下 T1 唤醒 T2、自己休眠，随后 T2 反向唤醒 T1」的乒乓模式，共四次系统调用、多次调度往返，社区给出了一条递进优化链：

flowchart LR
    A["wake + wait<br/>4 次系统调用"] -->|合并为 1 次调用| B["futex_swap<br/>切换耗时 -29.5%"]
    B -->|唤醒者选核=当前 CPU| C["+ prefer_current_cpu<br/>实测 -92.69%"]
    C -->|bypass 调度器| D["direct-thread-switch<br/>较基线 -37.1%（openEuler）"]

7.1 futex_swap（Google，Peter Oskolkov）

futex_swap(uaddr, val, abs_time, uaddr2)：一次系统调用内完成「唤醒 uaddr2 上至多一个等待者 next + 让自己 wait 在 uaddr 上」。为 SwitchTo（Google 闭源用户态调度框架）而设。

[!note] 魅族实测的泼冷水 移植到 Android 后与 FUTEX_WAKE_WAIT 耗时相差不大。拆解 trace：省下的 2 次系统调用发生在并行时间里，不在关键路径上，只降低系统整体负载。但「一次调用完成唤醒+休眠」为后续优化打开了接口。

7.2 wake_up_process_prefer_current_cpu

futex_swap 唤醒 next 时传入 WF_CURRENT_CPU 标志，select_task_rq_fair 选核时直接选中唤醒者所在 CPU。效果：两线程乒乓跑在同一个核上，schedule() 的 pick_next_task 大概率无缝选中对方。实测 3 轮切换 182µs → 18.4µs（10 倍），但拆解为：CPU 频率 5 倍（单核满载触发提频 500MHz→2.5GHz）× 调度效率 2 倍（免 idle 退出、尾延更低、cache 热）。patch 本身的净收益约 2 倍。与 Android binder 线程互醒场景同构，有移植价值。

7.3 direct-thread-switch（openEuler）

思想出自论文《The Case for Thread Migration》：执行实体与调度实体分离——线程切换时只换执行上下文，不换调度实体，新任务直接用原任务剩余时间片运行，bypass 选核/入队/负载更新，runnable 尾延归零。Linux 的 task_struct 把两者焊死多年，直接拆分不现实；于是基于 futex_swap，在 T1→T2 切换点用 __direct_thread_switch(next) 替代 schedule()，辅以「共享调度实体 shared sched_entry」保住 CFS 公平性。openEuler 数据：futex_swap 较基线 +29.5%，叠加 direct-thread-switch +37.1%。适用面窄：同步线程模型（典型即 IPC）。

7.4 futex vip 插队与继承（魅族落地手机场景）

  • 插队：等待队列里普通线程按 FIFO 排，前台 UX（vip）线程排不过 RT/普通线程 → 让 vip 插到 RT 之后、普通线程之前；设防饿死保护（队首普通线程等待超阈值则本次不插队）。
  • 继承：vip 线程等一把被普通线程持有的用户锁时，对 owner 临时授予 vip 特权（调度/IO/内存倾斜）直到它 futex_wake，解决用户空间锁的优先级反转。实现难点：futex 协议本身不携带 owner 信息，需扩展接口在 futex_wait 时传入 futex_info（含 owner_id）。

实测（模拟用户场景）：vip 等锁最大等待时间 -70%（重载 -67%），超 100ms 次数 -25%（重载 -38%），vip 等锁总时长 -24%（重载 -21%）。

8 陷阱清单

陷阱 后果 对策
不校验 EAGAIN / 不循环检查 丢失唤醒、死等 WAIT 前读值传入；醒后重查条件（见 §3 示例）
假设 WAIT 不虚假返回 条件未满足就往下走 等待逻辑必须包在循环里
拿 futex(2) 直接写应用同步 丢掉用户态快速路径，得不偿失 用 pthread_mutex / std::mutex
进程间共享却没放共享内存 fork 后 COW，各睡各的 shmget/mmap(MAP_SHARED)；op 带 shared 语义
忘记 FUTEX_PRIVATE_FLAG 内核走物理地址 key，白白变慢 线程内锁一律 private
std::atomic<int> 强转 int* 传 futex 平台相关 hack（x86-64 可用） 仅教学演示，勿进生产
