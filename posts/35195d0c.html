定义（Definition）

定义一个 Rust 类型系统可推理的对象，并用文字文档附上 Rust 无法推理的安全属性：

强制（Enforcement）

构造时建立不变量，修改时保持不变量，并且用封装（字段私有）堵住外部破坏的入口：

消费（Consumption）

对模块外的 safe 代码而言，"语言提供的安全保证"与"本模块提供的不变量"没有任何区别——违反两者的代码都编译不过。等于给 Rust 增加了一个新安全属性。

示例一：线程安全

Rust 引以为傲的线程安全并非语言特性，而是标准库用核心抽象实现的，原则上可以由第三方 crate 提供。

起点：spawn 必须走出语言边界

线程是 OS 概念，语言本身无法与线程交互，只能 unsafe 调系统 API：

unsafe 的含义：不是"必定出事"，而是"Rust 不够聪明、无法自证安全，程序员证明soundness"。

问题：不是所有值都能跨线程

上述 spawn 是 unsound 的——闭包可能捕获非线程安全的值。解法：把"线程安全"编码进类型系统。

实现：axiom 式声明 + 组合式传播

示例二：编译期死锁预防

问题：锁顺序不一致 → 死锁

sequenceDiagram
    participant TA as 线程 A
    participant TB as 线程 B
    TA->>TA: lock(ip) 成功
    TB->>TB: lock(device) 成功
    TA->>TA: 阻塞：等待 device
    TB->>TB: 阻塞：等待 ip
    Note over TA,TB: 互相持有对方想要的锁 → 死锁 💀

两个线程在"锁获取图"上形成环。思路：把无环锁顺序图编码进类型系统，且只允许沿图加锁。

第一步：给每个互斥锁命名

第二步：把锁顺序图编码为 trait

宏展开出的 blanket impl 使得一旦声明出环，impl 之间发生冲突，有环的图直接编译不过。

第三步：用 LockCtx 跟踪"当前在图上的位置"

签名里的三个机关：

  1. &mut LockCtx<L>：可变借用旧上下文 → 持锁期间旧上下文被"冻结"，不可复用；
  2. L: LockBefore<Id>：新锁必须是当前节点的下游 → 已持有的锁不可能再锁（无环）；
  3. 返回新 LockCtx<Id>：持锁期间唯一可用的上下文，且只允许继续往下游走。

收益

  1. 若整类 bug 在编译期消失，code review 与测试的压力骤减，开发速度有望大幅提升（不是取消 review，而是让它聚焦于真正需要人的部分）。
  2. 软件复杂度随代码规模超线性增长，且大多是偶然复杂度；人的心智容量有限，偶然复杂度会挤占对本质复杂度的推理能力，限制我们能解决的问题上限。该方法论在每个模块上省下的小额复杂度会在大型代码库中复利式叠加。
  3. AI 在这种类似问题场景下，缺少zero shot的能力。
